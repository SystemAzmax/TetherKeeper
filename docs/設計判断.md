# 設計判断（KeepAlive for Tethering / TetherKeeper）

指示書「Claudeへの重要な事前検討事項」1〜6 に対する検討結果と、実装で採った判断をまとめる。

---

## 1. Ping の実行要件

### Windows で管理者権限は必要か

**不要。** .NET の `System.Net.NetworkInformation.Ping` は Windows では
`IcmpSendEcho2`（iphlpapi.dll）を呼び出す。これは raw socket を使わないため、通常ユーザー権限で動作する。

- 確認済み: 管理者ではないユーザーで本アプリを起動し、`1.1.1.1` への Ping が成功した（応答 16 ms）。
- 単体テスト `PingKeepAliveStrategyTests` でも、`127.0.0.1` への Ping が昇格なしで成功する。

### OS ごとの動作可否

| OS | 動作 | 仕組み・注意点 |
|---|---|---|
| Windows | ◎ | `IcmpSendEcho2`。管理者権限は不要 |
| macOS | ○ | 非特権の ICMP データグラムソケット（`SOCK_DGRAM` + `IPPROTO_ICMP`）を使うため root は不要。使えない環境では `ping` コマンドの起動にフォールバックする。App Sandbox（Mac App Store 配布）下では要検証 |
| iOS / iPadOS | △ | raw socket は使えない。ICMP データグラムソケット自体は iOS でも使える（Apple の SimplePing サンプルが同方式）が、.NET for iOS での動作は実機検証が必要。プロセス起動によるフォールバックは使えない |

### .NET Ping API の制約

- 1 つの `Ping` インスタンスでは同時に 1 件しか送れない。本実装は毎回 `new Ping()` して破棄する。
- `PingOptions`（TTL / DontFragment）やバッファサイズの扱いは OS によって異なる。Linux/macOS では一部が無視される。
- 企業ファイアウォールや一部キャリアは ICMP を遮断する。この場合はタイムアウトになるため、HTTP HEAD への切り替えが必要。
- プロキシを経由しない（HTTP プロキシ必須の環境では外に出られない）。

## 2. 通信方式の比較

1 回あたりの通信量は IPv4 での概算（ヘッダ込み・往復）。

| 観点 | Ping (ICMP) | HTTP HEAD | TCP Connect |
|---|---|---|---|
| 1 回の通信量 | 約 120 B（32 B ペイロード） | 約 0.5〜1 KB（keep-alive で接続を再利用した場合）。新規接続時はハンドシェイク分が加わる。HTTPS は TLS 分さらに数 KB | 約 0.4 KB（SYN〜FIN の 6〜8 パケット） |
| 30 秒間隔・1 日 | 約 0.35 MB | 約 1.5〜3 MB（HTTP） | 約 1.2 MB |
| 権限 | 不要（Windows/macOS） | 不要 | 不要 |
| ICMP 遮断環境 | ✕ | ○ | ○ |
| HTTP プロキシ必須環境 | ✕ | ○（システムプロキシを使用） | ✕ |
| クロスプラットフォーム | OS 依存あり | ◎（iOS では `NSUrlSession` ベース） | ○ |
| 接続先への依存 | 低（ICMP 応答すればよい） | 中（HTTP サーバーが必要） | 高（ポートが開いている必要がある） |
| 実装 | `Ping.SendPingAsync` | `HttpClient.SendAsync`（HEAD） | `Socket.ConnectAsync` |

### プラットフォームごとの推奨

| プラットフォーム | 既定 | 理由 |
|---|---|---|
| **Windows** | **Ping** | 通信量が最小で、権限も不要。ICMP が遮断された環境では HTTP HEAD に切り替える |
| **macOS** | 直接配布なら **Ping**、Mac App Store 配布なら **HTTP HEAD** | サンドボックス下での ICMP の可否が不確実なため |
| **iOS / iPadOS** | **HTTP HEAD**（HTTPS） | iOS で最も確実に動く経路。ATS（App Transport Security）のため HTTPS URL にするか ATS 例外を設定する |

本アプリは 3 方式すべてを実装し、設定画面で切り替えられる（既定は Ping）。

## 3. iPhone / iPadOS の制約

### 前提: どの端末でアプリを動かすか

アイドル切断を防ぐには、**テザリングの子機側**（iPad、Mac、PC など）からテザリング回線を通る通信を発生させる必要がある。
親機の iPhone 自身で本アプリを動かしても、子機とのリンクには通信が流れないため効果は期待できない。
iOS 版の主な用途は「iPad / 別の iPhone を子機として使う場合」になる。

### バックグラウンド実行の制限

- アプリがバックグラウンドへ移ると、数秒〜約 30 秒でサスペンドされる。
- `beginBackgroundTask` で延長できるのは最大約 30 秒だけ。
- `BGTaskScheduler`（BGAppRefreshTask）の実行タイミングは OS が決める。間隔は最短でも 15 分程度が目安で、実行される保証もない。数十秒間隔の定期通信には使えない。
- 「定期通信」のためのバックグラウンドモードは存在しない。audio / location / VoIP を目的外に使うと審査でリジェクトされる。

### 定期タイマーの制約

- サスペンド中はタイマーも止まる。確実に動くのは**フォアグラウンドかつ画面点灯中**だけ。
- 画面ロックを防ぐ `UIApplication.IdleTimerDisabled` を併用する「表示中のみ動くモード」が現実的な上限になる。

### App Store 配布時の課題

- **2.5.4**: バックグラウンドモードは本来の目的にしか使えない。
- **4.2 最低限の機能**: 単機能のユーティリティはリジェクトされるリスクがある。
- **ATS**: 平文 HTTP は既定でブロックされるため、HTTPS を使う必要がある。
- バッテリー消費に関する説明が求められる可能性がある。

**結論:** iOS 版は「フォアグラウンド表示中だけ動く補助ツール」として設計する。Windows 版と同等の常駐動作は実現できない。

## 4. Windows スリープ時の挙動

| 検討事項 | 挙動 | 本実装での対応 |
|---|---|---|
| スリープ中は停止するか | **停止する。** S3 スリープではプロセス全体が止まる。Modern Standby（S0 低電力アイドル）でもデスクトップアプリは抑制され、Wi-Fi も切断されることが多い | 防ぐ処理は入れない（ユーザーの電源設定を尊重するため） |
| 復帰後に再開するか | ループは止まらないため、**自動で再開する** | `SystemEvents.PowerModeChanged`（Resume）を受け、`ResumeDelay`（既定 5 秒）後に即時実行する。復帰直後はアダプタが再接続中のことが多いため少し待つ |
| 電源イベントが取れない場合 | — | 前回実行からの経過時間が「間隔 × 2 + タイムアウト」を超えたら、スリープ復帰の可能性としてログを出す（OS 非依存の保険） |
| 追加対応が必要か | 必須ではない | 将来のオプション候補は下記のとおり |

将来のオプション候補:

- `SetThreadExecutionState(ES_SYSTEM_REQUIRED)` による動作中のスリープ抑止。
- Wi-Fi アダプタの省電力設定の案内。

## 5. UI フレームワークの選定（MAUI vs WinUI 3）

| 観点 | .NET MAUI | WinUI 3 |
|---|---|---|
| クロスプラットフォーム性 | ◎ Windows / macOS（Catalyst）/ iOS / Android を単一プロジェクトで扱える | ✕ Windows のみ |
| 保守性 | ○ 1 つのコードベースで済む。ただしプラットフォーム差異への対応が必要 | ◎ Windows だけなら API が素直 |
| 学習コスト | ○ XAML / MVVM の知識が流用できる。Shell 等の MAUI 固有概念がある | ○ WPF / UWP 経験者には低い |
| 将来性 | ○ .NET 本体と同じリリースサイクル。Windows 上の描画は WinUI 3 | ○ Windows App SDK として継続 |
| Windows 固有機能 | △ `Platforms/Windows` で WinUI 3 API を直接呼べる | ◎ |

**採用: .NET MAUI。** 将来の macOS / iOS 展開が要件にあるため。
MAUI の Windows 版の中身は WinUI 3 なので、Windows 固有の処理（トレイ常駐など）が必要になっても `Platforms/Windows` 配下で対応できる。

## 6. 最終的な実装方針

```text
TetherKeeper.slnx
├─ KeepAlive.Core            OS 非依存（Models / Interfaces / Services / Strategies / Configuration）
├─ KeepAlive.Infrastructure  OS 依存（JSON 設定保存 / HKCU\Run 自動起動 / SystemEvents 電源通知）
├─ TetherKeeper              .NET MAUI UI（指示書の KeepAlive.Maui に相当）
└─ KeepAlive.Tests           xUnit（Strategy / Settings / KeepAliveWorker）
```

- **依存方向**: `TetherKeeper → Infrastructure → Core`。Core は UI と OS のどちらにも依存しない。
- **Strategy パターン**: `IKeepAliveStrategy` を 3 方式で実装する。`IKeepAliveStrategyResolver` が設定値から実装を選ぶ。
- **DI**: Core 側は `AddKeepAliveCore()`、Infrastructure 側は `AddKeepAliveInfrastructure()` で登録する。OS ごとの差し替えは Infrastructure 内で行う。
- **MVVM**: CommunityToolkit.Mvvm（`[ObservableProperty]` / `[RelayCommand]`）を使う。
- **テスト容易性**: 時刻はすべて `TimeProvider` 経由で扱い、テストでは `FakeTimeProvider` で仮想時間を進める。

### 指示書との差異（要確認）

| 項目 | 指示書 | 実装 | 理由 |
|---|---|---|---|
| .NET バージョン | .NET 8 | **.NET 10**（Core は .NET 8 でもビルド可能） | ① .NET 8 のサポートは 2026-11-10 に終了する。.NET 10 は LTS で 2028-11 までサポートされる。② MAUI 8 は 2025-05 にサポートが終了している。③ 開発環境には .NET 10 SDK と MAUI 10 ワークロードしか入っていない。④ 既存の TetherKeeper プロジェクトも net10.0 だった。Core は net8.0 でもビルドできることを確認済み |
| UI プロジェクト名 | KeepAlive.Maui | TetherKeeper | 既存のソリューション・プロジェクトを活かした。役割は同じ |
| `IKeepAliveStrategy` | `Name` / `ExecuteAsync` | 上記に `Method` プロパティを追加 | 設定値（列挙型）から Strategy を選択するため |
| TcpConnectKeepAliveStrategy の利用 API | 指示書の記述が途中で切れている | `Socket.ConnectAsync`（デュアルスタック） | 接続確立のみ行い、すぐに `Shutdown` する |
| `AppSettings` の項目 | 指定なし | 方式、間隔、タイムアウト、各接続先、起動時自動開始、ログイン時起動 | — |
