# 設計判断（KeepAlive for Tethering / TetherKeeper）

指示書「Claudeへの重要な事前検討事項」1〜5 に対する検討結果と、実装で採った判断をまとめる。

---

## 1. Ping の実行要件

### Windows で管理者権限は必要か

**不要。** .NET の `System.Net.NetworkInformation.Ping` は Windows では
`IcmpSendEcho2`（iphlpapi.dll）を呼び出す。これは raw socket を使わないため、通常ユーザー権限で動作する。

- 確認済み: 管理者ではないユーザーで本アプリを起動し、`1.1.1.1` への Ping が成功した（応答 16 ms）。
- 単体テスト `PingKeepAliveStrategyTests` でも、`127.0.0.1` への Ping が昇格なしで成功する。

### OS ごとの動作可否

| OS | 動作 | 仕組み・注意点 |
|---|---|---|
| Windows | ◎ | `IcmpSendEcho2`。管理者権限は不要 |
| macOS | ○ | 非特権の ICMP データグラムソケット（`SOCK_DGRAM` + `IPPROTO_ICMP`）を使うため root は不要。使えない環境では `ping` コマンドの起動にフォールバックする。App Sandbox（Mac App Store 配布）下では要検証 |

### .NET Ping API の制約

- 1 つの `Ping` インスタンスでは同時に 1 件しか送れない。本実装は毎回 `new Ping()` して破棄する。
- `PingOptions`（TTL / DontFragment）やバッファサイズの扱いは OS によって異なる。Linux/macOS では一部が無視される。
- 企業ファイアウォールや一部キャリアは ICMP を遮断する。この場合はタイムアウトになるため、HTTP HEAD への切り替えが必要。
- プロキシを経由しない（HTTP プロキシ必須の環境では外に出られない）。

## 2. 通信方式の比較

1 回あたりの通信量は IPv4 での概算（ヘッダ込み・往復）。

| 観点 | Ping (ICMP) | HTTP HEAD | TCP Connect |
|---|---|---|---|
| 1 回の通信量 | 約 120 B（32 B ペイロード） | 約 0.5〜1 KB（keep-alive で接続を再利用した場合）。新規接続時はハンドシェイク分が加わる。HTTPS は TLS 分さらに数 KB | 約 0.4 KB（SYN〜FIN の 6〜8 パケット） |
| 30 秒間隔・1 時間 | 約 14〜19 KB | 約 72〜138 KB（HTTP。接続の作り直しを含む） | 約 48〜72 KB |
| 30 秒間隔・1 日 | 約 0.35 MB | 約 1.5〜3 MB（HTTP） | 約 1.2 MB |
| 権限 | 不要（Windows/macOS） | 不要 | 不要 |
| ICMP 遮断環境 | ✕ | ○ | ○ |
| HTTP プロキシ必須環境 | ✕ | ○（システムプロキシを使用） | ✕ |
| クロスプラットフォーム | OS 依存あり | ◎ | ○ |
| 接続先への依存 | 低（ICMP 応答すればよい） | 中（HTTP サーバーが必要） | 高（ポートが開いている必要がある） |
| 実装 | `Ping.SendPingAsync` | `HttpClient.SendAsync`（HEAD） | `Socket.ConnectAsync` |

### プラットフォームごとの推奨

| プラットフォーム | 既定 | 理由 |
|---|---|---|
| **Windows** | **Ping** | 通信量が最小で、権限も不要。ICMP が遮断された環境では HTTP HEAD に切り替える |
| **macOS** | 直接配布なら **Ping**、Mac App Store 配布なら **HTTP HEAD** | サンドボックス下での ICMP の可否が不確実なため |

本アプリは 3 方式すべてを実装し、設定画面で切り替えられる（既定は Ping）。

## 3. Windows スリープ時の挙動

| 検討事項 | 挙動 | 本実装での対応 |
|---|---|---|
| スリープ中は停止するか | **停止する。** S3 スリープではプロセス全体が止まる。Modern Standby（S0 低電力アイドル）でもデスクトップアプリは抑制され、Wi-Fi も切断されることが多い | 既定では防がない（ユーザーの電源設定を尊重するため）。設定の「キープアライブの動作中はスリープしない」をオンにした場合だけ、動作中の自動スリープを抑止する（「初版以降に追加した機能」を参照） |
| 復帰後に再開するか | ループは止まらないため、**自動で再開する** | `SystemEvents.PowerModeChanged`（Resume）を受け、`ResumeDelay`（既定 5 秒）後に即時実行する。復帰直後はアダプタが再接続中のことが多いため少し待つ |
| 電源イベントが取れない場合 | — | 前回実行からの経過時間が「間隔 × 2 + タイムアウト」を超えたら、スリープ復帰の可能性としてログを出す（OS 非依存の保険） |
| 追加対応が必要か | 必須ではない | 将来のオプション候補は下記のとおり |

- ~~動作中のスリープ抑止~~（2026-11-24 に設定として実装済み）。
- Wi-Fi アダプタの省電力設定の案内。

## 4. UI フレームワークの選定（MAUI vs WinUI 3）

| 観点 | .NET MAUI | WinUI 3 |
|---|---|---|
| クロスプラットフォーム性 | ◎ Windows / macOS（Catalyst）/ Android を単一プロジェクトで扱える | ✕ Windows のみ |
| 保守性 | ○ 1 つのコードベースで済む。ただしプラットフォーム差異への対応が必要 | ◎ Windows だけなら API が素直 |
| 学習コスト | ○ XAML / MVVM の知識が流用できる。Shell 等の MAUI 固有概念がある | ○ WPF / UWP 経験者には低い |
| 将来性 | ○ .NET 本体と同じリリースサイクル。Windows 上の描画は WinUI 3 | ○ Windows App SDK として継続 |
| Windows 固有機能 | △ `Platforms/Windows` で WinUI 3 API を直接呼べる | ◎ |

**採用: .NET MAUI。** 将来の macOS 展開が要件にあるため。
MAUI の Windows 版の中身は WinUI 3 なので、Windows 固有の処理（トレイ常駐など）が必要になっても `Platforms/Windows` 配下で対応できる。

> 2026-11-24 追記: macOS 版は、MAUI（Mac Catalyst）ではなく、AppKit で別のプロジェクトとして作ることにした（「6. macOS 版を AppKit のメニューバー常駐アプリとして別に作る」）。
> Windows 版は MAUI のまま変えない。

## 5. 最終的な実装方針

```text
TetherKeeper.slnx
├─ KeepAlive.Core            OS 非依存（Models / Interfaces / Services / Strategies / Configuration）
├─ KeepAlive.Infrastructure  OS 依存（JSON 設定保存 / HKCU\Run 自動起動 / SystemEvents 電源通知）
├─ TetherKeeper              .NET MAUI UI（指示書の KeepAlive.Maui に相当。Windows 版）
├─ TetherKeeper.Mac          macOS 版の UI（AppKit のメニューバー常駐アプリ。TetherKeeper.Mac.slnx でビルドする）
└─ KeepAlive.Tests           xUnit（Strategy / Settings / KeepAliveWorker）
```

- **依存方向**: `TetherKeeper → Infrastructure → Core`。Core は UI と OS のどちらにも依存しない。
- **Strategy パターン**: `IKeepAliveStrategy` を 3 方式で実装する。`IKeepAliveStrategyResolver` が設定値から実装を選ぶ。
- **DI**: Core 側は `AddKeepAliveCore()`、Infrastructure 側は `AddKeepAliveInfrastructure()` で登録する。OS ごとの差し替えは Infrastructure 内で行う。
- **MVVM**: CommunityToolkit.Mvvm（`[ObservableProperty]` / `[RelayCommand]`）を使う。
- **テスト容易性**: 時刻はすべて `TimeProvider` 経由で扱い、テストでは `FakeTimeProvider` で仮想時間を進める。

### 実装しなかったもの（今後の候補）

- ~~macOS（Login Items）向けの Infrastructure 実装~~ 2026-11-24 に macOS 版の最小の版を作り始めた（「6. macOS 版を AppKit のメニューバー常駐アプリとして別に作る」）。スマートフォン版は別アプリとして作成する方針
- MSIX の自動更新（`.appinstaller`）。Microsoft Store で公開するため、ストア版はストアが自動で更新する。`.appinstaller` が効くのは `build/Publish-Msix.ps1` で作る自己署名の MSIX を直接配る場合だけで、そのために置き場所（共有フォルダや HTTPS の Web サーバー）を用意して管理する価値は小さいため、作らない。直接配る MSIX は、新しい `.msix` を手動でインストールして更新する（README の「更新」を参照）
- 正式なコード署名証明書（認証局の証明書や Azure Trusted Signing）への移行。Microsoft Store で公開するため、ストア版はストアが署名し、証明書の購入や各 PC での信頼登録は要らない。`build/Publish-Msix.ps1` で作る自己署名の MSIX は、開発中の確認や手元の PC への配布用として、今の仕組み（自己署名証明書と信頼登録）のまま残す

| 通信量の上限での自動停止 | `KeepAlive.Core/Services/DataUsageTracker.cs`、`KeepAlive.Infrastructure/Network/NetworkInterfaceDataUsageMeter.cs`、`KeepAliveWorker` | アプリ自身の通信量ではなく、通信に使われているアダプターの送受信量（ほかのアプリの通信を含む）を数える。テザリングの通信量の上限を守るには、実際の消費量に近い方がよいため。アダプターは UDP ソケットの Connect（パケットは送らない）で決まる送信元アドレスから判定する。数えるのはキープアライブ動作中だけ（自宅の回線などテザリング以外の通信を数えないため）。累計はリセットするまで再起動をまたいで加算し、設定の変更通知と干渉しないよう `settings.json` とは別のファイルに保存する。上限は 1 MB = 1,000,000 バイトとして、早めに止まる側に寄せる |
| 連続失敗・復旧の通知 | `KeepAlive.Core/Services/FailureAlertTracker.cs`、`Platforms/Windows/TrayController.cs`、`NotifyIcon.cs`、`IconBadge.cs` | 1 回の失敗は一時的なことがあるため、既定は 3 回連続で「切れている」とみなす。同じ失敗の状態では 1 回だけ通知し、復旧は失敗を通知したあとだけ通知する（失敗が続いた時間も出す）。判定は統計（`KeepAliveStatistics`）と別に数え、利用者が統計をリセットしても影響しないようにする。停止したら状態を忘れ、次の開始時の成功を「復旧」としない。通知はトレイアイコンのバルーン（Windows 11 ではトースト）を使い、パッケージ版・非パッケージ版のどちらでも同じ仕組みで出す。トレイアイコンの赤い丸は、アプリのアイコンから実行時に作る（画像ファイルを別に持たず、アイコンを変えても合う）。通知をオフにしても赤い丸は付ける。通知の設定だけを変えたときは、Worker は通信し直さない |
| 動作中のスリープ抑止 | `KeepAlive.Core/Interfaces/ISleepInhibitor.cs`、`KeepAlive.Infrastructure/Power/WindowsSleepInhibitor.cs`、`KeepAliveWorker` | 電源の設定を尊重するため既定はオフ。抑止するのは自動スリープだけで、画面の消灯は妨げない（`PowerRequestSystemRequired` だけを使い、`DisplayRequired` は使わない）。`SetThreadExecutionState` ではなく電源要求（`PowerCreateRequest` / `PowerSetRequest`）を使う。電源要求はスレッドに結び付かないため Worker のスレッドプールから切り替えられ、理由の文字列が `powercfg /requests` に出るため、スリープしない原因を確かめられる。切り替えは Worker の開始・停止（自動停止を含む）と設定の変更で行い、抑止の失敗ではキープアライブを止めずにログに残す。Windows の仕様で、利用者の操作（ふたを閉じる、電源ボタン、スタートメニューの「スリープ」）によるスリープは防げず、モダン スタンバイの PC をバッテリーで使うと、スリープまでの時間を過ぎてから 5 分で要求が打ち切られる |
| 自動停止の拡張（相対時間・毎週・アプリの終了） | `KeepAlive.Core/Models/WeeklyDays.cs`、`KeepAliveWorker`、`MainViewModel`、`AppExitService` | 「1 時間後」「2 時間後」は、画面で日時を計算して既存の予約に渡すだけにした（秒は切り上げ、指定より早く止まらないようにする）。毎週の自動停止は、1 回限りの予約（`AutoStopAt`）とは別の設定にし、停止しても解除しない。次の停止は「開始した日時」より後で最初に来る曜日・時刻とし、動作中に毎週の設定を変えたときは「変えた日時」から数え直す（変える前に過ぎた時刻ですぐ止まらないようにする）。同じ日時なら予約として扱い、予約を解除できるようにする。アプリの終了は UI 層の `AppExitService` の役目のため、Worker は停止の理由（`AutoStopReason`）を `AutoStopped` で知らせるだけにし、終了は UI 側で行う。終了するのは日時の予約と毎週の自動停止のときだけで、通信量の上限で停止したときは、理由を画面で確かめられるよう終了しない。対になる「決まった時刻に開始」は、ネットワークに応じた自動開始で多くの場面をまかなえるため、入れていない |
| 送信先の予備（予備の通信方式） | `AppSettings.FallbackMethod`、`KeepAliveWorker`、`KeepAliveStatistics` | 予備は「別の通信方式」として選び、送信先はその方式の設定欄の値を使う。既定の送信先は方式ごとに違う（Ping と TCP は 1.1.1.1、HTTP は msftconnecttest.com）ため、方式を変えるだけで「別のホスト」と「別の方式」の両方を変えられ、設定の項目も増やさずに済む。通信方式と同じ方式は選べない。やり直すのは通信方式で失敗したときだけにして、通信量の増加を抑える。予備で成功したら回線はつながっているとみなし「成功」として数える（連続失敗も 0 に戻り、失敗の通知も出ない）。統計には予備で成功した回数を別に数え、ログには「予備で成功」と残す。どちらも失敗したら、通信方式の結果に予備の失敗の内容を添えて 1 回の失敗とする。予備の方式は失敗したときだけ使うため、予備の設定を変えても通信し直さない |
| 英語対応 | `KeepAlive.Core/Resources/CoreStrings.resx`、`TetherKeeper/Resources/Strings/AppStrings.resx`（それぞれ `.ja.resx` が日本語）、`KeepAlive.Core/Models/AppLanguages.cs`、`KeepAlive.Core/Services/AppLanguageStartup.cs` | 既定ではアプリ名と同じく表示言語（`CurrentUICulture`）で決め、日本語なら日本語、それ以外は英語にする（MSIX の既定の言語も en-US）。設定画面の「言語（Language）」で選び直せる。選択肢はコンボボックスにして、言語を足すときは `AppLanguages.Supported` に 1 行と `.resx` を足すだけにした。選択肢は各言語自身の名前で出し、見出しには英語の「Language」を添える（読めない言語を選んでしまっても戻せるようにするため）。画面の文言はページを作るときに読み込むため、言語の変更はその場で切り替えず、再起動で反映する（全ページを作り直すより確実なため）。再起動は Windows App SDK の `AppInstance.Restart`（パッケージ版・非パッケージ版の両方で使える）で行い、その前に終了と同じ後片付けをする。新しいプロセスは再起動の引数（`--restarted`）を受け取り、前のプロセスが終わるまで多重起動の判定を待つ。選んだ言語は、設定の読み込み（非同期）を待たずに、起動のいちばん初めに設定ファイルから直接読んで反映する。数値や日時の書式は Windows の地域の設定のままにする。スタート メニューなどに出るアプリ名（MSIX のマニフェスト）は Windows が決めるため、選んだ言語には従わない。画面だけでなく、ログ・通知・入力エラーも訳す（ログは画面に出すため）。Core の文言（Worker のログ、`AppSettings.Validate` のエラーなど）は Core にリソースを持たせ、文言を返す今の形のままにした（コードを返して UI で文言にする形は、変更が大きいわりに得るものが少ないため）。リソースのクラスはビルド時に `.resx` から作る（Visual Studio のデザイナーに頼らない）。WinUI の XAML コンパイラーは通常のコンパイルの前にソースを一度コンパイルするため、`AppStrings` をその前に作るターゲットを csproj に足した。履歴の CSV は表示言語で書き、読むときはどの言語の文言も受け付けて、言語を切り替えても読めるようにした。開発者向けのデバッグ出力は日本語のまま。テストは表示言語に左右されないよう日本語に決め、英語と日本語のリソースの項目と埋め込み先がそろっていることをテストで確かめる |
| 履歴の集計・エクスポート | `KeepAlive.Core/Services/ResultHistory.cs`、`ResultCsv.cs`、`KeepAlive.Infrastructure/History/CsvResultHistoryStore.cs`、`Views/HistoryPage.xaml` | 統計（`KeepAliveStatistics`）はメモリ上だけで再起動で消えるうえ、ログの文面から集計すると文面を変えたときに壊れるため、通信の結果をログとは別に日ごとの CSV に記録する。保存日数はログと同じ 30 日で、日ごとのファイルの名前と古いファイルの削除はログと共通の `DailyFiles` にまとめた。ファイルの形式は、書き出す CSV と同じにして（`ResultCsv`）、そのまま Excel でも開けるよう UTF-8 の BOM と「2026/11/24 10:23:45」形式の日時にした。集計は PC の時刻の時間帯（0〜23 時）ごとに、回数と失敗の割合を出す。時間帯によって通信した回数が違うため、棒は回数ではなく失敗の割合にする。書き出し先は、MSIX 版の保存先（LocalState）が奥深く分かりにくいため、ダウンロード フォルダーにし、書き出したファイルをエクスプローラーで選んだ状態で開く（保存先を選ぶダイアログには追加のライブラリが要るため使わない）。記録は画面を開く前から始めるよう、`MauiProgram` でアプリの起動時に `ResultHistory` を作る |

| ネットワークに応じた自動開始・停止 | `KeepAlive.Core/Services/NetworkAutoControl.cs`、`KeepAlive.Core/Interfaces/INetworkMonitor.cs`、`Platforms/Windows/WindowsNetworkMonitor.cs` | ネットワークの名前は WinRT の接続プロファイルの名前（`ConnectionProfile.ProfileName`）で判定する。Windows 11 24H2 から、SSID を返す WLAN API（`WlanQueryInterface`）や `Windows.Devices.WiFi` は位置情報の許可が必要になったが、接続プロファイルの名前は対象外のため、許可を求めずに使える。また、Wi-Fi だけでなく USB や Bluetooth のテザリングも同じ方法で判定できる。名前は大文字と小文字を区別する（SSID は区別されるため）。接続の「変化」で開始・停止し、今の状態に合わせ続けることはしない。そのため、接続中に利用者が自分で止めたら、つなぎ直すまで開始しない。ほかのネットワークで自分で開始したものも止めない。接続の変化の通知は 1 回で何度も来るうえ、Wi-Fi は一瞬切れてすぐつながり直すことがあるため、最後の通知から 5 秒待ってから判定する。対象のネットワークや有効・無効を変えたら前回の判定を忘れ、オンにした時点で接続中ならすぐに開始する。停止すると失敗の通知が出なくなるため、切断で停止したときは失敗の通知と同じ設定で通知する。WinRT の API は MAUI の Windows 向けのプロジェクトでしか使えないため、Infrastructure は「未対応」の実装を登録し、`MauiProgram` で差し替える（MSIX 版の自動起動と同じ方法）。起動直後に既定の設定で動かないよう、設定を読み込んでから `ActivateAsync` で動かし始める |

## 6. macOS 版を AppKit のメニューバー常駐アプリとして別に作る

2026-11-24 に決めた。Microsoft Store で 1.0.0 を公開する準備ができたあと、macOS 版の作り方を検討した。

### 作り方の比較

| 案 | 内容 | 評価 |
|---|---|---|
| A. 今の MAUI アプリを Mac Catalyst でも動かす | 画面（XAML）と ViewModel をそのまま使える | △ Mac Catalyst は iPad のアプリを Mac で動かす仕組みのため、メニューバー常駐（`NSStatusItem`）を直接作れない。AppKit のプラグインを別に作って読み込む必要があり、かえって複雑になる。ウィンドウを閉じても動き続ける作りとも合わない |
| B. `net10.0-macos`（AppKit）でメニューバー常駐アプリを作る | 画面は作り直す。Core と Infrastructure、文言のリソースは共有する | ◎ Mac で自然な形（Dock に出ず、メニューバーから操作する）にでき、Mac の API をすべて使える |
| C. Swift で作り直す | Mac として最も自然 | ✕ コードを共有できず、2 つを別々に保守することになる |

**採用: B。** 画面は Mac の作法に合わせて作り直し、キープアライブの処理（Worker、設定、通知の判定、履歴など）は Windows 版と同じコードを使う。

### 決めたこと

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 配布 | Mac App Store | Windows 版と同じく、署名と更新をストアに任せる。サンドボックスで動かす必要がある（`Entitlements.plist` は `app-sandbox` と `network.client` だけ） |
| 最小の版の範囲 | メニューバーでの状態の表示、開始・停止、今すぐ実行、設定（言語・通信方式・送信先・間隔・通知・起動）、失敗と復旧の通知、ログイン時の起動 | 本来の目的（切断を減らす・切断に気づく）に要るものを先に作り、Mac で動きを確かめてから残りを足す |
| 対応する macOS | 13 以降 | ログイン項目の登録（`SMAppService`）が macOS 13 からのため。それより前の `SMLoginItemSetEnabled` は、別のヘルパー アプリが要り複雑になる |
| プロジェクト | `TetherKeeper.Mac`（`net10.0-macos`）と `TetherKeeper.Mac.slnx` | macOS 版は Mac でしかビルドできない。`TetherKeeper.slnx` に入れると Windows でのビルドが通らなくなるため、ソリューションを分ける |
| MAUI のビルド対象 | Windows だけにし、使っていなかった Android と Mac Catalyst を外した | 使わない対象のためにワークロードを入れたり、ビルドの時間をかけたりしないため |
| 画面の文言 | Windows 版の `AppStrings.resx` をそのまま取り込み、Mac だけの文言は `MacStrings.resx` に置く | 同じ文言の訳を二重に持たないため。「Windows」を含む文言（ログイン時の起動、言語の既定など）は Mac 用に別に用意する。どちらも `LocalizationTests` が .resx を直接読んで、英語と日本語の項目がそろっているかを確かめる |
| 表示言語 | 設定の言語が空なら、`NSBundle.MainBundle.PreferredLocalizations`（Info.plist の `CFBundleLocalizations` の中から macOS が選んだ言語）を使う | macOS では、システム設定の「言語と地域」でアプリごとに言語を選べる。それにも従うため。言語を読む処理（`AppLanguageStartup`）は、Windows 版と共有するため Core に移した |
| 言語を変えたとき | 次に起動したときに切り替わる（Windows 版のような再起動はしない） | サンドボックスの中で自分を起動し直す方法は、確かめてからにする |
| 設定の保存先 | Application Support の下の `TetherKeeper` フォルダ（サンドボックスのコンテナの中） | Windows 版と同じ構成のファイル（settings.json、logs、history）にして、Infrastructure の実装をそのまま使う |
| 終了 | `applicationShouldTerminate:` で、キープアライブを止めてログを書き出してから終わる | メニューの「終了」だけでなく、ログアウトや再起動のときも同じ後片付けをするため |

### Mac で確かめること

Windows では macOS 版をビルドできないため、最初の版は Mac で一度もビルドしていない。確かめる手順は [MacBuildGuide.md](MacBuildGuide.md) の「最初に確かめること」にまとめた。特に次の 2 つは、結果によって作りを変える。

- **サンドボックスの中の Ping**: .NET の `Ping` は、macOS では非特権の ICMP ソケット（`SOCK_DGRAM`）を使う。サンドボックスの `network.client` の権限で使えるかは未確認。使えなければ、macOS 版の既定の通信方式を HTTP HEAD か TCP 接続にする。
- **ネットワークの名前（残りの機能）**: macOS 14 以降、Wi-Fi のネットワーク名（SSID）を読むには位置情報の許可が要る。ネットワークに応じた開始・停止を作るときに、許可を求めるか、インターフェースの種類（Wi-Fi、USB など）で判定するかを決める。
